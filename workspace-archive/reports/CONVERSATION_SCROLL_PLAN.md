**Conversation scrolling: follow-up diagnostic plan**

Executed on 28 September 2026. See [findings and saved evidence](CONVERSATION_SCROLL_FINDINGS.md). The text below records the original plan.

Prepared 28 September 2026, after [PR #191](https://github.com/tobagin/karere/pull/191) shipped. The user reports that the chat list is much smoother, but conversation scrolling remains less responsive or smooth, including in mostly text-only conversations. This plan covers diagnosis; no new scrolling measurements or application changes have been made for this follow-up.

**Verified starting point**

- Installed Flathub stable: Karere 4.3.2, commit `534efc4dd04bbba5248e5927fde32b7da09af1e0bc25e2795eee3f47a62b915a`.
- Its manifest references annotated tag object `952a12f3412cd35afa1606514f7d967a5b5447aa`, resolved through GitHub to v4.3.2 source commit `11dfc0e62d7279e5dd3b2e97dc096e521845dedb`.
- Runtime is now GNOME 51; the previous investigation used GNOME 50. The x86_64 CEF archive remains 152.0.6 / Chromium 152.0.7977.83, with the same archive SHA-256 as the earlier package. A CEF patch added to the source repository is not proof that the bundled CEF binary incorporates it.
- Stored GPU Rendering preference is off, zoom is 1.0, and Reduce Motion is off. Actual rendering path, GPU, scale, window size and power state must be recorded during each capture. Karere was not running during this inspection.
- [Previous validation](upstream/tools/scrolling-probe/FIX_VALIDATION.md) measured programmatic scrolling of `#pane-side`, the chat list. GTK draw callbacks improved from approximately 10 to 60 per second. It did not measure conversation scrolling, physical input latency, or compositor presentation timing.
- The [released source](https://github.com/tobagin/karere/blob/v4.3.2/src/cef_runtime.rs) still adds `disable-smooth-scrolling`. The input bridge converts wheel and touchpad deltas before sending them to CEF. The CPU-buffer rendering path copies damaged regions and uploads them to an OpenGL texture. These are testable leads, not established explanations for the remaining symptom.

**Investigation sequence**

1. **Make the comparison reproducible.** Start with one already-open, mostly text-only conversation. Keep the same loaded section, application dimensions, zoom, display, refresh rate and power condition. Let startup settle for at least 20 seconds, then use a 5-second warmup and three 20-second samples. Keep steady scrolling inside loaded history separate from reaching the boundary that loads older messages. Use the chat list in the same window as a control. Compare the same conversation in the regular browser; record its engine/version and add an available Chromium browser only if an engine comparison becomes necessary. Recheck current display settings instead of assuming the previously measured 60 Hz / 190% scale is unchanged.

2. **Separate input from rendering.** Extend the existing probe to find and verify the conversation's scroll container using geometry and a reversible small movement. Exclude `#pane-side`; refuse to report success unless the intended container actually moves. Restore its initial position afterwards. Compare a repeatable JavaScript `scrollTop` trajectory, wheel input injected through CEF or Chromium's input interface, and genuine wheel/touchpad input. The first measures page/rendering capacity, the second adds browser input processing, and the third includes the GTK-to-CEF bridge. A JavaScript-dispatched `WheelEvent` is not a substitute for native input. Measure both initial response and sustained motion; record distance, event spacing and motion after release as well as frame gaps. Automated runs can cover the first two paths; physical-device claims require a real input sample.

3. **Locate the delay in the pipeline.** Add buffered, in-process timestamps and correlate them across clocks: GTK event arrival and handler entry → forwarding to CEF → page scroll/rAF → CEF work/paint → frame copy or import → GTK draw → presentation, where available. Record CEF work requests, pump duration and overdue deadlines, including long gaps without a paint callback. Record dirty pixel area, bytes copied/uploaded, lock wait and CPU time by process/thread. For page work, collect layout, paint, raster and script timing; the Long Tasks API alone misses work shorter than 50 ms that can still disrupt a 60 Hz display. Report p50/p95/p99 and worst gaps, missed refresh intervals, and input-to-frame delay. GTK draw callbacks and page rAF are proxies; report actual presentation only when the backend exposes usable presentation feedback. Keep a control with tracing disabled to detect observer overhead.

4. **Follow the evidence using one-variable comparisons.** Use the table below to select the next experiment. Do not run every possible graphics, runtime and power combination upfront. Alternate baseline/change/change/baseline, repeat the comparison, and hold the scroll range and workload constant. For changes affecting scroll distance, also compare at matched achieved scroll speed so extra pixel movement is not mistaken for extra rendering cost.

| Observation | Next controlled comparison | What it distinguishes |
| --- | --- | --- |
| JavaScript scrolling is smooth; native input is delayed or uneven | Compare CEF-injected input with physical input; inspect units, scaling, event spacing, fractional accumulation and gesture endings | Browser input processing versus the GTK input bridge |
| Frames arrive regularly, but movement jumps between events | Build the same release with only `disable-smooth-scrolling` removed; compare first response, motion and stopping separately for each device | Abrupt motion versus late frames; enabling animation could improve appearance while increasing latency |
| Conversation scrolling is slow even with JavaScript | Compare CPU-buffer and verified AMD DMA-BUF rendering at identical dimensions; measure copy/upload and wait times | Frame-transfer cost versus earlier page/browser work |
| Cost rises with dirty pixel area | Use generated text conversation content at matching pane sizes, then vary pane width/backing resolution separately | Pixel bandwidth and scaling cost versus WhatsApp layout complexity |
| Page layout/script/raster work stalls while pump and host rendering remain prompt | Compare loaded history with the history-loading boundary, and real text conversations with a generated equivalent; inspect expensive task stacks | WhatsApp virtualization/history work, rasterization or Karere's injected integration code |
| Long CEF pump gaps remain, particularly without paint | Correlate pending work, schedule callbacks and work-slice exits; compare a narrowly instrumented continuation fix | A remaining scheduling failure beyond the frame-triggered continuation addressed by #191 |
| CEF delivers timely frames, but GTK/presentation falls behind | Inspect main-thread work, upload/fence waits and frame-clock timing; only then isolate GNOME 50/51 or display scale with otherwise matched app/CEF builds | Host rendering, runtime or compositor behavior |

Text-only conversations are the primary workload. Add media-heavy content after the text-only case is understood, to find any additional decoding or animation cost. The earlier manual GPU and smaller-window comparisons were inconclusive and do not rule out a bottleneck in this new workload.

5. **Require a reversible explanation before implementing a fix.** A candidate cause must explain a measured delay, improve the relevant metric when changed, and reproduce the delay when reverted. Improvement should exceed run-to-run variation. Confirm the result on both conversation and chat-list scrolling, with wheel and touchpad input, then check native menu responsiveness, both supported frame-transfer paths, and settled visible/background CPU. Multiple causes may remain: smoother motion does not establish lower input latency, and a higher average callback rate does not establish consistent presentation.

**Execution notes and deliverable**

Reuse `tools/scrolling-probe`, adding a conversation target, a generated conversation-sized workload and stage timing. Revalidate CEF probe ABI assumptions against the installed build before reuse. Build any diagnostic variant from the shipped v4.3.2 source in an isolated checkout; the existing local checkout and `run-fixed.sh` belong to the previous investigation, and the launcher pins the old Flatpak deployment. Use temporary launch settings and restore each baseline. Collect timing, geometry and aggregate counts without chat text, contacts, cookies or screenshots; inspect any trace fields before sharing upstream.

The first useful result is a matched chat-list/conversation capture that identifies the stage responsible for delayed or uneven motion. The final diagnostic report should include the reproducer, exact builds and settings, per-stage measurements, repeated change/revert evidence, remaining limitations, and a narrowly scoped fix proposal. If generated content reproduces the problem, use it as the shareable regression workload.
